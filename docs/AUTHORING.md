# Window Authoring Format (TypeScript) — v5

UI sources live in the pack source under `window/`. The rpp plugin loads every `window/**/*.ts` and `window/**/*.tsx`
file, passes the default-exported window and HUD definitions to the compiler, and removes those sources from the built
pack. Art is generated by Window, or references PNGs under `window/` by pack-source-relative path.

`window/index.ts` (or `window/index.tsx`) is the entry: it default-exports
`defineWindows({ windows, huds, sprites, fonts, previews })`, imported from `plugin:window/ui`, listing every window and
HUD of the pack, the [sprite catalog](#sprite-catalog), the [text fonts](#text-fonts), and any [previews](#previews).
`windows` and `huds` take definitions or the documents `<Window>`, `<Hud>`, `raw.ui(...)`, and `raw.hud(...)` return.
Lists may nest, so a module default-exporting a fragment or an array of HUDs can be listed as one entry. An entry of the
wrong kind, such as a HUD in `windows`, is a type error where its type is known and a build error otherwise. Every other
file under `window/` is an ordinary module, such as one declaring [handles](#handles), that the entry imports.

```ts
import { defineWindows } from "plugin:window/ui";

import { searchField } from "./art.ts";
import search from "./search.tsx";
import shop from "./shop.tsx";
import statusHuds from "./status_hud.tsx";

export default defineWindows({ sprites: { searchField }, windows: [shop, search], huds: statusHuds });
```

Without an entry, every file under `window/` default-exports `raw.ui(...)` or `raw.hud(...)`, or, in a `.tsx` file, a
[JSX](#jsx-sources) `<Window>`, `<Hud>`, or a fragment of several; the build warns and reads them in path order.

UIs are written as [JSX](#jsx-sources) from a few [primitives](#primitives), with [handles](#handles) declaring their
bindings and [`industrial`](#industrial) providing ready-made controls. The function-style [`raw` API](#raw-api) builds
the same primitives as plain function calls. `pattern` and the slot refs serve both styles.

The authoring API is split into modules:

| module                           | exports                                                                                  |
| -------------------------------- | ---------------------------------------------------------------------------------------- |
| `plugin:window`                  | the `window()` plugin entry for `rpp.config.ts`                                          |
| `plugin:window/ui`               | primitives, `defineWindows`, slot refs and `pattern`, art, styles, vars, and their types |
| `plugin:window/bind`             | [handles](#handles) and their types                                                      |
| `plugin:window/raw`              | the [`raw` API](#raw-api), imported as `import * as raw from "plugin:window/raw"`        |
| `plugin:window/theme/industrial` | the [`industrial`](#industrial) components, art, colors, and styles                      |

The authoring API is typed. Run `rpp codegen` in the pack project to generate the SDK typings these modules resolve
against for autocomplete and type checking.

## Plugin options

`window()` in `rpp.config.ts` takes these options. An unknown key fails the build, naming the key and the accepted keys.

```ts
window({
  namespace: "miningsim",
  coreShaders: { hud: true },
  vanilla: {
    anvil: { field: "search_field", background: false },
    hud: { hotbar: false, health: false, food: false, armor: false, air: false, experience: false, crosshair: false },
  },
  experimental: { anvilUpdates: true },
  size: { report: true, budget: 3_000_000 },
  previews: { output: "build/previews" },
  kotlin: { package: "com.example.generated", output: "src/main/kotlin/generated", target: "minestom" },
});
```

- `namespace`: namespace of the generated assets. Defaults to `window`.
- `coreShaders.hud`: emit the core text shaders that place [`<Hud anchor>`](#roots) HUDs. Opt-in, and sensitive to the
  client version.
- `coreShaders.hover`: emit the core text shaders that draw region [hovers](#hover). Opt-in, and sensitive to the client
  version.
- `experimental.anvilUpdates`: lets [anvil input windows](#native-anvil-search) change their title at runtime.
- `size.report`: print a breakdown of the compiler's output after a successful build; see
  [What things cost](#what-things-cost).
- `size.budget`: a positive byte count. A build whose output exceeds it fails, stating the budget, the total, the
  overage, and the breakdown. Omitted means no limit.
- `previews.output`: the directory, relative to the project root, that [previews](#previews) are written to.
- `kotlin`: generate Kotlin bindings into `output`; `target` is `minestom`, `multistom`, or `agnostic`.

### Vanilla textures

Every `vanilla` value follows one rule: a string names a [catalog sprite](#sprite-catalog) that replaces the vanilla
texture, `false` replaces it with a transparent texture of the same size, and `true` or omitted leaves vanilla alone. A
catalog sprite must be generated or bundled, not external, and match the size of the texture it replaces.

- `vanilla.anvil.field` covers the two anvil text-field sprites (110x16).
- `vanilla.anvil.background` covers the anvil background (256x256) and the missing-result error icon. Omitted, both are
  blanked exactly when some window has an anvil `<Input>`; `false` always blanks them; `true` keeps vanilla's even with
  an input. A string replaces the background and blanks the error icon.
- `vanilla.hud.<group>` takes only booleans. `false` blanks every vanilla GUI sprite of the group under
  `assets/minecraft/textures/gui/sprites/hud/`, and needs pack format 18 (Minecraft 1.20.2) or newer:
  - `hotbar`: the hotbar, its selection, offhand, and attack-indicator sprites.
  - `health`: every heart, including hardcore, blinking, absorbing, frozen, poisoned, withered, and vehicle hearts.
  - `food`, `armor`, `air`: their full, half, and empty sprites, and the hunger and bursting variants.
  - `experience`: the experience bar, plus the jump bar and locator bar that replace it.
  - `crosshair`: the crosshair and its attack indicator.

- `vanilla.slotHighlight` covers the highlight vanilla draws on the hovered slot (24x24), in every container screen and
  the player's inventory, and needs pack format 42 (Minecraft 1.21.2) or newer. A string replaces the part drawn over
  the slot's item and blanks the part drawn under it.

Blanking sprites cannot hide HUD text, such as the experience level number or the held item name.

### Overriding files

rpp fails the build when a generated file would replace a file the pack's own source owns, for example under
`assets/minecraft/shaders/core/` or a vanilla texture that a `vanilla` option overrides. Overrides that come from
separately loaded packs or mods cannot be detected at build time, so the load order decides which one wins.

### What things cost

`size: { report: true }` prints where the compiler's output bytes go, largest first within each part:

```
Window output: 534.9 KB (compiler output, before pack optimization)
  win shop                     9.8 KB   static 3.3 KB · 33 switch cases 6.5 KB
  hud status_bottom_center     2.7 KB   static 0 B · 20 switch cases 2.7 KB
  sprite fonts (3)             1.2 KB   largest sprite_y29 389 B
  text-row fonts (11)        189.2 KB   largest small_caps/y137 17.2 KB
  kotlin (17)                195.5 KB
  debug descriptor           108.4 KB
  main font                   11.4 KB
```

- Each window and HUD line is its total, split into its static art and its switch cases. The count is every case; a case
  that draws art bakes its own texture, so a switch costs roughly the number of such cases times one case's art. Cut
  cases, or move art that every case repeats out of the switch.
- A line also counts its art layers when it has any: the textures of art with a [`tint` handle](#tints), of untinted art
  drawn over it, and of the clips of each [bar](#bars)'s fill.
- Each distinct vertical position that a text slot (or line of a multi-line slot) draws at adds one text-row font
  document, and a custom font adds one per position. Sprite slots add one sprite font per position, listing every
  catalog sprite. Aligning slots to fewer rows removes fonts. HUDs pinned with [`<Hud anchor>`](#roots) are aligned to
  each other and to windows automatically.
- The remaining lines are shared: runtime sprite textures, text font sheets, the main font document, generated HUD
  shaders, vanilla overrides, the debug descriptor, and generated Kotlin.

Sizes are the bytes the compiler emits (pack files plus generated Kotlin), before rpp's later squash and optimize step,
so the shipped pack is smaller. Each file counts whole toward one line. Documents that grow with every window, such as
the main font and the debug descriptor, are reported as their own lines and are not split among windows.

`size.budget` turns the same report into a build check. Older rpp builds failed large outputs with wasmtime's "fuel
allocated for hostcalls has been exhausted"; this was a plugin host limit that newer rpp (the version `plugin/rpp.json`
requires) no longer hits, but a budget keeps growth visible before it reaches a limit elsewhere.

## Previews

A preview is a PNG of one window or HUD, drawn by the compiler from the same layout and art as the pack, with the handle
values you give it. Declare previews next to the UI and set `previews.output`; every `rpp build` then writes
`<name>.png` into that directory.

```ts
import { defineWindows, preview } from "plugin:window/ui";

export default defineWindows({
  windows: [shop],
  huds: [status],
  previews: [
    preview(shop, [
      [category, "gear"],
      [balance, "1,250"],
      [canBuy, true],
      [tabLabel, ["All", "Gear", "Magic"]],
      [products, { count: 12, selected: 3 }],
    ]),
    preview(status, [[lamp.at(2), true]], { name: "status-lit", scale: 3, outlines: true }),
  ],
});
```

`preview(target, state?, options?)` takes a window or HUD as `windows` and `huds` list it (one document, not a fragment
of several), a list of `[handle, value]` entries, and:

- `name`: the file stem, lowercase letters, digits, `_`, and `-`. Defaults to the window's or HUD's name, so two
  previews of one target need a `name`.
- `scale`: an integer from 1 to 16 that upscales the image with nearest-neighbour sampling. Defaults to 1, one image
  pixel per GUI pixel.
- `outlines`: outline the active [regions](#primitives), which otherwise draw nothing.

An image may hold at most 16,777,216 pixels (4096 x 4096) after scaling; a larger one fails the build naming the
preview, its size, and its scale.

Each entry's value is typed by its handle, and a handle the entry omits takes its default:

| handle       | value                                | default                                    |
| ------------ | ------------------------------------ | ------------------------------------------ |
| `text`       | a string, `§` codes allowed          | empty: the slot draws nothing              |
| `flag`       | a boolean                            | `false`                                    |
| `toggle`     | a boolean                            | its `initial`, else `false`                |
| `value`      | one of its values                    | its first value                            |
| `selection`  | one of its values                    | its `initial`, else its first value        |
| `tint`       | one of its palette entry names       | its first palette entry                    |
| `fraction`   | a number from 0 to 1                 | `1`: the bar is full                       |
| `sprite`     | a catalog sprite name, of its `only` | no sprite                                  |
| `items`      | whether the slot holds an item       | `true`                                     |
| `collection` | `{ count?, selected? }`              | every cell holds an item; none is selected |
| `input`      | the typed string                     | the input's `initial`                      |

An [indexed handle](#indexed-handles-and-repeaters) takes a list with one value per member, nested once per dimension
(members left out keep their default), or `handle.at(i)` sets one member. Actions have no state. An entry for a handle
the target does not use, or with a value of the wrong kind, fails the build naming the preview and the handle.

A window's image covers its container's GUI rectangle and a HUD's its `width` x `height`, each grown to cover any art
that bleeds outside it, on a transparent background. What it shows:

- **As the client draws it**: static art, the active case of every switch (nested ones too), runtime sprites in their
  slots, a collection's `selected` sprite, a `vanilla.anvil.field` sprite, and text in a [text font](#text-fonts),
  including the bundled `small_caps`. Art and text with a [`tint` handle](#tints) take the color of the tint's previewed
  palette entry, at their place in the [draw order](#draw-order). Text is placed, wrapped, and ellipsized by the rules
  the runtime applies, with the slot's width, alignment, color, shadow, and bold. Text state may carry legacy `§` codes,
  consumed as the runtime consumes them: `§l` draws bold, `§0`-`§f` draw that color (and end bold), `§r` restores the
  slot's color and bold, and any other code is consumed without effect. A trailing `§` is dropped.
- **Approximately**: text in Minecraft's default font. Window cannot bundle Mojang's glyph bitmaps, so each character is
  drawn as its `small_caps` glyph, centered in and clipped to the real glyph's width, or as a box when `small_caps` has
  no glyph for it. Advances are the real ones, so the text occupies exactly the box it does in game, but the lettering
  differs. An anvil input's typed text is drawn the same way.
- **As a placeholder**: inventory items. The compiler has no item models, so each item slot, filled collection cell, and
  anvil input slot is a thin magenta outline.
- **Not at all**: vanilla's own textures (an anvil's background, the inventory behind a window), italic, underline,
  strikethrough and obfuscation (their `§` codes are consumed but draw nothing), and anything the server decides at
  runtime, such as a text component carrying its own color, or a tooltip.

Previews are not pack output: they are written outside the pack and do not count toward the
[size report or budget](#what-things-cost). Without `previews.output`, declared previews are not rendered and the build
warns that nothing is written. A build that declares none does no preview work.

## Text fonts

`defineWindows({ fonts })` declares bitmap text fonts by name, which text selects with `font`:

```ts
export default defineWindows({
  fonts: {
    runes: {
      texture: "window/fonts/runes.png",
      chars: ["abcdefgh", "ijklmnop"],
    },
  },
  windows: [shop],
});
```

```tsx
<Text font="runes">abc</Text>
```

Each `chars` row maps one row of equally wide, 8px-tall sheet cells, left to right; `"\u0000"` leaves a cell empty and
every mapped cell needs at least one opaque pixel. Cells sit on the text line like vanilla `ascii.png` cells, with seven
rows above the baseline and one below, so glyph art carries its own vertical placement. Characters the sheet does not
map fall back to vanilla glyphs. Window measures each glyph from the sheet, so layout and runtime alignment match what
the client draws. Font names are unique across the pack; a name declared twice is a build error.

Window bundles a `small_caps` font: letters of either case as 5px small capitals, digits, and common punctuation,
centered on vanilla capital height. `smallCaps` (`small_caps` in `raw`) is shorthand for `font: "small_caps"`; a font
named `small_caps` replaces the bundled one.

## JSX Sources

`.tsx` sources describe windows and HUDs as JSX. They compile to the same elements as the `raw` API, and the compiler
lays them out with [taffy](https://github.com/DioxusLabs/taffy) (CSS flexbox and grid), so most UIs need no coordinates.
Both styles can be mixed in one pack.

rpp compiles `.tsx` sources with its own JSX runtime, `rpp:jsx`: each tag calls the component with its props, and
`<>...</>` is an array of its children. `rpp codegen` configures type checking for it; packs only need `**/*.tsx` in
their `tsconfig.json` `include`. Sources import only Window's components, never a JSX factory.

```tsx
import { Box, Text, Window } from "plugin:window/ui";
import { action, collection, selection, text } from "plugin:window/bind";
import { Button, Collection, Container, Header, Hotbar, Tabs, art } from "plugin:window/theme/industrial";

const category = selection("category", ["all", "gear", "magic"]);
const products = collection("products", { selectable: true });

export default (
  <Window name="shop" container="generic_9x6" frame={art.shell} text={{ color: "#ffffff", smallCaps: true }}>
    <Header>
      <Text>Foundry Exchange</Text>
    </Header>
    <Container frame={art.panel}>
      <Tabs bind={category} span={3}>
        {(value) => <Text>{value}</Text>}
      </Tabs>
      <Collection bind={products} rows={3} />
      <Box span={9} frame={art.recess} direction="row" align="center" padding={{ left: 4, right: 4 }}>
        <Text bind={text("selection")} />
        <Text bind={text("price")} width={40} align="right" />
      </Box>
    </Container>
    <Hotbar>
      <Button onClick={action("buy")} span={6} style={{ base: { frame: art.buttonAccent } }}>
        <Text bind={text("buy_label")} />
      </Button>
      <Button close span={3}>
        Exit
      </Button>
    </Hotbar>
  </Window>
);
```

The example pack's `window/` sources are a complete project: `index.ts` lists the documents, `art.ts` declares its art,
`handles.ts` declares the windows' handles, `shop.tsx`, `search.tsx`, `upgrades.tsx`, and `status_hud.tsx` use them in
JSX, and `clock_hud.ts` is a HUD written with the [`raw` API](#raw-api).

### Slot sections

`<Section of="container" | "player" | "hotbar">` is a slot section: a CSS grid with one track per inventory slot. Its
children auto-flow through the grid left to right, top to bottom, and each child covers its grid area:

- `span={n}` or `span={[columns, rows]}` sizes the area (default 1x1); `at={[x, y]}` places it at a zero-based slot;
  `col`/`row` take raw one-based CSS grid lines (`{ start, end, span }`; negative lines count from the end).
- Regions, items, and collections bind the slots of their area. A `pattern` on items or a collection is relative to its
  area; raw `slots` opt out of the grid.
- Any other child is a visual cell covering the area's 18x18 slot boxes: a box fills the cell, and text or art is
  centered in it. `translate` moves visual cells in pixels.
- Section children support grid placement and visual translation. Put pixel sizing, alignment, margins, and absolute
  positioning inside a box so they cannot change which inventory slots a child owns.
- A child or its relative pattern that does not fit its area or the section is an error.
- `frame` draws around the section's slot boxes, grown by `outset` (3 by default).
- Slots no child owns are claimed (`claim="unowned"`) so vanilla items do not show through; set `claim="none"` to leave
  them alone, or `claim="all"` to claim every slot. `flow` sets the grid auto-flow (`"row"`, `"column"`, `"row-dense"`,
  `"column-dense"`).

Industrial's `Container`, `Player`, and `Hotbar` are sections of each kind.

### Boxes

`<Box>` is a flexbox, or a grid with `display="grid"`. It takes CSS container properties (`direction`, `wrap`,
`justify`, `align`, `alignContent`, `gap`, `padding`, `width`, `height`, min/max sizes, `aspectRatio`, grid
`columns`/`rows`, and `flow`) and an optional `frame` of [inline art](#inline-art) drawn over its rect. Lengths are
pixels, `"N%"`, or a sizing keyword; grid tracks also accept `"Nfr"`. Padding and gaps accept only pixels or
percentages; margins and insets also accept `"auto"`.

- An auto-sized box placed directly in the window, a HUD, a switch case, or a section cell fills it; a box with `x`/`y`
  (or inside a row or column) takes its content size.
- Children take item properties: `grow` (`true` is 1), `shrink`, `basis`, `alignSelf`, `justifySelf`, `margin`, grid
  placement, and `absolute` with `top`/`right`/`bottom`/`left`. `x`/`y` position a child absolutely.
- `translate={[x, y]}` moves an element and its subtree after layout.
- Text is at least 8px tall and vertically centered in its box, and `align` positions it within the box's width. Text
  without `width` stretches across a vertical box under the default stretch alignment; in a horizontal one static text
  takes its content width and `<Text bind>` grows to fill the box.
- Images keep their size and are centered in their box.
- A `<Region>`, `<Items>`, or `<Collection>` without its own slots covers its box and claims the inventory slots the box
  covers.

### Primitives

Every window is built from a few primitives, which the [`industrial`](#industrial) components are made of:

| primitive                                          | `raw` equivalent              | notes                                                                   |
| -------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------- |
| `<Window>`, `<Hud>`                                | `ui`, `hud`                   | roots                                                                   |
| `<Box>`                                            | `box`                         | flexbox or grid; `frame` is [inline art](#inline-art), `tint` colors it |
| `<Text>` / `<Text bind>`                           | `text`                        | static text, or dynamic text bound by a `text` handle                   |
| `<Image art>` / `<Image bind size>`                | `image`                       | art drawn at its own size, or a runtime sprite slot bound by a handle   |
| `<Bar bind width height fill>`                     | `bar`                         | a [bar](#bars) filled up to the fraction a `fraction` handle returns    |
| `<Switch bind><Case value>…</Case></Switch>`       | `switchOn(on, cases)`, `case` | `bind` is a value, selection, flag, or toggle handle, or a condition    |
| `<Region onClick? tooltip? itemModel?>`            | `region`                      | slots that take clicks and show a hitbox item                           |
| `<Items bind>`, `<Collection bind>`                | `items`, `collection`         | real item stacks                                                        |
| `<Input bind>`                                     | `input`                       | the anvil's rename field                                                |
| `<Section of="container" \| "player" \| "hotbar">` | `section(kind)`               | slot grids; see [Slot sections](#slot-sections)                         |

- A region without `width` and `height` fills its parent box and claims the slots the box covers; in a section it claims
  its `span`/`at` area. Its `onClick` is an `action`, `selection.set(value)`, `toggle`, or `builtin`; without one it
  only shows its `tooltip` and hitbox item.
- A region may cover slots whose stacks an `<Items>` or `<Collection>` shows: it routes clicks on every slot it covers
  and fills its hitbox item only into the others. A click on an action collection's cell still goes to the collection.
- Switch cases may hold regions, items, and collections, including in nested switches. Their slots are claimed only
  while their case is drawn, so regions and items in mutually exclusive cases may cover the same slots: a click routes
  to the region of the case selected when it arrives, and the items swap with the case. Two regions, or two item
  controls, covering the same slot outside mutually exclusive cases are a build error.
- Every primitive takes `debugName`, which build errors name (``… (in `buy-hitbox`)``) and the inspector shows as the
  source of the layers it draws.

A tab group built from primitives:

```tsx
<Section of="container">
  {category.values.map((value) => (
    <Box span={3} padding={1} debugName={`tab-${value}`}>
      <Switch bind={category.is(value)} grow>
        <Case value="true" frame={tabSelected} />
        <Case value="false" frame={tab} />
      </Switch>
      <Region onClick={category.set(value)} tooltip={labels[value]} />
    </Box>
  ))}
</Section>
```

A section cell spans its slots' 18x18 boxes, while a control's face covers their 16x16 interiors, hence the `padding`.

### Hover

With the plugin option `coreShaders: { hover: true }`, the client draws an outline or authored art over a region while
the cursor is over one of its slots. Vanilla highlights only the single hovered slot, which
`vanilla: { slotHighlight: false }` removes.

```tsx
<Button onClick={buy} span={6}>Buy</Button> // a 1px white outline: it takes clicks
<Button onClick={sort} span={3} hover={false}>Sort</Button> // nothing
<Hotspot tooltip="Balance" span={3} hover /> // outlined although it takes no clicks
<Button onClick={close} hover={texture("ui/close_hover.png")}>X</Button> // this art, in its own colors
```

- A region draws the white outline of its rectangle by default when it has an `onClick`. `hover` overrides that on
  `<Region>` and on the industrial controls built on one (`Button`, `Toggle`, `Choice`, `Tabs`, `Repeater`, `Hotspot`):
  `true` for the outline, `false` for nothing, or [inline art](#inline-art). A control passes it only to the states that
  take clicks. Setting `hover` while `coreShaders.hover` is off is a build error.
- Hover art is drawn in its own colors and alpha, over everything else in the window. Art that stretches, which is a
  texture with `insets` or a shape without `width` and `height`, covers the region's rectangle as a `frame` would. Other
  art is drawn at its own size and centered on the region, so art 2px wider and taller than the region surrounds it by
  1px; when the sizes differ by an odd amount the art sits the odd pixel toward the top-left. Art may extend past the
  region and the window. Pixels under 10% alpha are not drawn, and a texture id from another pack cannot be hover art.
- The hover is drawn with the region's hitbox item, so a region with a hover and no tooltip still fills its slots; its
  tooltip box is hidden. Slots where an `<Items>` or `<Collection>` shows a stack show that stack's tooltip and no
  hover.
- An outline or hover art is 4 to 256 px wide, at most 254 px tall, and starts within 128 px of the GUI's center; a
  region outside those limits fails the build until its art is resized or its `hover` is `false`.
- The outline's color and thickness are fixed; use art for anything else. [Previews](#previews) do not draw hovers.
- It needs pack format 85 through 88 (Minecraft 26.2 is 88), shares `core/text` with `coreShaders.hud`, and like it
  depends on the client version. Where the hover crosses the region's own tooltip it is cut out, using the tooltip size
  the server measures; advanced tooltips (F3+H) add lines the server cannot see, so the hover may show through them. A
  tooltip the server cannot measure exactly (such as a translatable component) or that is wider than 2047 px or longer
  than 29 lines gets no cut-out, so the whole hover is drawn and may show through the tooltip.

### Inline art

`texture(path, options?)` and `shape(style, options?)` author art values. A box, section, case, window, or HUD `frame`
stretches art over its laid-out size; `<Image art>` draws it at its own size. Frame and image props take only art
values.

```ts
import { shape, texture } from "plugin:window/ui";

export const bevel = shape({ kind: "button", fill: "#3a3a3a" }, { name: "industrial/button" });
export const panel = texture("window/panel.png", { insets: 4 });
export const coin = texture("window/coin.png");
export const lamp = shape({ kind: "badge", fill: "#ffb20b", width: 8, height: 8 });
```

- `texture` takes a pack-source-relative path or a texture id such as `"example:item/coin.png"`, nine-slice `insets` for
  frames (a number or `{ top, right, bottom, left }`), and `width`/`height` (set together) for images. A texture id
  drawn as an image must set `width` and `height`, because Window does not infer its size from the pack source.
- `shape` takes a generated style, plus `width` and `height` to draw it as an image. `kind` is `"panel"`, `"button"`,
  `"slot"`, `"hazard_bar"`, `"vent"`, or `"badge"`. Common options are `fill`, `border_color`, `border_width`, `radius`,
  `inset_depth`, `highlight_color`, `shadow_color`, `accent_color`, `indicator_color` (panel, button, and slot only),
  `stripe_color`, `stripe_shadow_color`, and `stripe_width`.
- Art is named by a hash of its content, prefixed by its optional `name`: `art/industrial-button-3fa2c1`. Identical art
  is shared.
- `tint` on a `<Box>` or `<Case>` with a `frame`, or on an `<Image>`, multiplies the art's colors by a color: a hex
  color is baked into the art at build time, and a [`tint` handle](#tints) picks the color at runtime.

### Sprite catalog

`defineWindows({ sprites })` names art that Kotlin selects at runtime. Each entry becomes a `WindowSprite` constant, and
a `sprite` handle declared with `only` returns a generated enum of just those sprites:

```ts
export const lamp = sprite("lamp", { only: ["lamp_on", "lamp_off"] });

export default defineWindows({
  sprites: { lamp_on: texture("window/lamp_on.png"), lamp_off: texture("window/lamp_off.png") },
  windows: [panel],
});
```

```tsx
<Image bind={lamp} size={8} />
```

The view declares `enum class LampSprite(val sprite: WindowSprite) { LAMP_ON, LAMP_OFF }` and
`protected abstract fun lampSprite(): LampSprite?`. Catalog names are unique across the pack, and every `only` entry
must be a catalog sprite. Vars in catalog art take their default values.

For each distinct vertical offset of a sprite slot, Window emits a `sprite_y...` font whose bitmap providers reference
the same sprite texture files with the appropriate ascent, so one texture is placed at several heights without
duplicating PNGs. For bitmap sprites, the runtime cursor advance matches Minecraft: it is based on the rightmost
non-transparent pixel after scaling to the sprite height, plus the client's one-pixel bitmap gap. Transparent padding
affects alignment through the sprite's measured visible ink bounds.

### Styles

`create` declares named styles: the props a primitive takes for its frame, layout, and text, written once and passed
through `style`. Each property is typed as on the primitive, and unknown properties are errors.

```tsx
import { Box, Text, create, shape, variants } from "plugin:window/ui";

const s = create({
  tab: variants({
    base: { frame: shape({ kind: "button", fill: colors.face }), padding: 2 },
    selected: { frame: selectedArt, translate: [0, -2] },
  }),
  wide: { width: 64 },
  label: { color: "#ffffff", shadow: true },
});

<Box style={[s.tab.base, wide && s.wide]} padding={4}>
  <Text style={s.label}>Buy</Text>
</Box>;
```

- `style` takes a style, a falsy value (skipped), or a nested array of them; later entries win per property, and
  explicit props win over the style.
- Each primitive takes only the properties it understands, also from styles stored in variables: `<Box>` takes its
  frame, container properties, item properties, and `text`; `<Text>` text and item properties; `<Image>`, `<Region>`,
  and `<Items>` item properties; `<Collection>` also `frame`; `<Switch>` also `text`; `<Case>` and `<Hud>` the box
  properties except item placement; `<Section>` and `<Window>` `frame` and `text`. A style with `color` on a `<Box>` is
  a type error. `BoxStyle`, `TextStyle`, `ItemStyle`, and the other `*Style` types name each set.
- `variants({ ... })` marks a group of named styles that a component chooses among. A group is not a style, so it cannot
  be passed to a primitive; pass one of its variants. The names mean nothing to Window: a component declares the ones it
  takes, and the style each must be, with `Variants`:

```tsx
import type { BoxStyle, Variants } from "plugin:window/ui";

function Tab(props: { selected: boolean; style?: Partial<Variants<"base" | "selected", BoxStyle>> }) {
  return <Box style={[props.style?.base, props.selected && props.style?.selected]} />;
}

<Tab selected style={s.tab} />; // a group with a variant Tab does not name is a type error
```

### Vars and themes

`defineVars` declares vars with their default values, `#rrggbb` colors or numbers. A var stands for its value in styles,
props, and `shape()` fields, and carries its value's type: a color var is a type error where a number belongs.
`createTheme(vars, overrides)` overrides some of them, typed by the vars, for the subtree of the `<Window>`, `<Hud>`, or
`<Box>` whose `theme` it is.

```tsx
import { Box, Text, Window, createTheme, defineVars, shape } from "plugin:window/ui";

const colors = defineVars({ face: "#0994c6", text: "#ffffff" });
const space = defineVars({ pad: 2 });
const ember = createTheme(colors, { face: "#c0503a" });

<Window name="shop" container="generic_9x6" text={{ color: colors.text }}>
  <Box frame={shape({ kind: "button", fill: colors.face })} padding={space.pad} />
  <Box theme={ember}>
    <Box frame={shape({ kind: "button", fill: colors.face })} />
  </Box>
</Window>;
```

- `<Window>` and `<Hud>` resolve every var when they are built: each takes its value from the nearest `theme` above
  where it is used, or its default. The compiler sees only values, so each resolved art is its own content-hashed art.
- Inherited `text` styles resolve where the text is, under the text's nearest theme.
- `derive(get => value)` computes a value from resolved tokens each place it is used; `get` resolves a var under the
  theme there. Art recipes use it to derive colors from a themed fill. `mix(from, to, amount)` blends two colors:

```ts
import { derive, mix, shape } from "plugin:window/ui";
import type { Color, Token } from "plugin:window/ui";

const raised = (fill: Token<Color>) =>
  derive((get) => {
    const base = get(fill);
    return shape({
      kind: "button",
      fill: base,
      highlight_color: mix(base, "#5ff0ff", 0.45),
      shadow_color: mix(base, "#020a30", 0.4),
    });
  });

<Box frame={raised(colors.face)} />; // a different bevel under each theme
```

### Roots

| root                                                 | `raw` equivalent | notes                                                            |
| ---------------------------------------------------- | ---------------- | ---------------------------------------------------------------- |
| `<Window name container frame? bleed? text?>`        | `ui(...)`        | `frame` is drawn first over the GUI grown by `bleed`             |
| `<Hud name channel? width? height? anchor? offset?>` | `hud(...)`       | children lay out as a column; without a size it fits its content |

`text={{ ... }}` on a window, HUD, section, box, or switch sets default text style (`color`, `shadow`, `bold`, `italic`,
`underlined`, `strikethrough`, `obfuscated`, `font`, `smallCaps`, `align`) for the text inside it; the nearest setting
wins.

`containerLayout(container)` is the geometry the compiler lays a window out over, in GUI pixels: the screen's `width`
and `height`, the `title` origin, and each section's `columns`, `rows`, 16x16 slot interiors (`slots`), and their
`bounds`; for an anvil, also the native `input` field. Its types follow the container, so
`containerLayout("generic_9x3").sections.container.rows` is `3` and only an anvil's layout has `input`. Components use
it to place art around a container's slots:

```tsx
const { player } = containerLayout("generic_9x6").sections;

<Image art={vent} x={52} y={player.bounds.y - 8} />;
```

`<Hud anchor>` pins the HUD with the generated core shaders (requires `coreShaders.hud`): `"top-left"`, `"top"`,
`"top-right"`, `"left"`, `"center"`, `"right"`, `"bottom-left"`, `"bottom"`, `"bottom-right"`, or a normalized
`{ x, y }`. The same point of the HUD is placed on that screen point, and `offset={[x, y]}` nudges it in GUI pixels.

Pinned HUDs share text-row fonts without any authoring. The shader decides where a pinned HUD lands, so the compiler is
free to bake the whole HUD (art, switch cases, and text) some rows higher or lower in the actionbar and have the HUD's
shader rule subtract the same rows; nothing moves on screen. HUD by HUD in name order, it picks the shift whose text
rows reuse the most [text-row fonts](#what-things-cost) that windows and earlier HUDs already need, and the smallest
such shift. Rows can only coincide where their spacing matches, so pinned HUDs that use the same line pitch share every
font, whatever `y` their first row is on. HUDs without `anchor` are not shifted, and neither are HUDs with authored
`underlined`, `strikethrough` or `italic` text (static labels, dynamic slots, and text inside switch cases), because
Minecraft draws those decorations from the unshifted baseline and shears italics by the glyph ascent. The compiler
cannot see styling a server applies inside a bound text value, such as an Adventure component; on a pinned HUD, such an
underline or strikethrough is positioned from the text baseline rather than the row, and italics may drift sideways, so
set the style on the element when you need it.

The size limit of a pane is the size of its art. A pane's static art, and each switch case's art, bakes into one font
glyph, and the client keeps glyphs on 256x256 px font atlas pages. A glyph larger than that in either direction is never
placed on a page: the client does not draw it, and it misplaces everything sent after it. Such art is therefore a build
error that names the pane, the art, and its size; keep each piece of art within 256 px each way, or split the pane. This
applies to windows and every HUD. Text is not limited this way and may continue below the art. In particular a pinned
HUD is not limited by where the actionbar sits: with the default `sourceBottom` of 59, row 0 is baked 72 px above the
bottom of the GUI (59 plus Minecraft's 13 px actionbar inset), and rows from 72 on are baked below the screen edge,
which the client still draws once the shader has moved them.

## Industrial

`plugin:window/theme/industrial` is Window's default look as plain components built from the [primitives](#primitives)
and [handles](#handles). Its art is inline, and its runtime state is switches on handles. Industrial components are
functions, so the `raw` API calls them directly: `Button({ onClick, children })`. Its `Collection` shares a name with
the primitive; a file using both renames one on import.

```tsx
import { Text } from "plugin:window/ui";
import { action, collection, flag, selection, text } from "plugin:window/bind";
import { Button, Collection, Container, Hotbar, Tabs, Window, art } from "plugin:window/theme/industrial";

const category = selection("category", ["all", "gear", "magic"]);
const products = collection("products", { selectable: true });

<Window name="shop" container="generic_9x6" title="Foundry Exchange">
  <Container frame={art.panel}>
    <Tabs bind={category} span={3}>
      {(value) => <Text>{value}</Text>}
    </Tabs>
    <Collection bind={products} rows={3} />
  </Container>
  <Hotbar>
    <Button onClick={action("buy")} enabled={flag("can_buy")} disabled={{ tooltip: "Too expensive" }} span={6}>
      <Text bind={text("buy_label")} />
    </Button>
    <Button close span={3}>
      Exit
    </Button>
  </Hotbar>
</Window>;
```

| component                                               | notes                                                                                    |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `Button onClick \| close, enabled?, disabled?`          | `disabled` (`tooltip`, `itemModel`, `frame`) shows while `enabled` is false; no clicks   |
| `Toggle bind on? off?`                                  | flips a `toggle` handle; `on`/`off` are its states                                       |
| `Choice bind value selected? unselected?`               | sets a selection to `value`                                                              |
| `Tabs bind sprite? selectedSprite? tooltip? itemModel?` | one `Choice` per value; children render each value, or are `Tab value tooltip?` elements |
| `Repeater cell columns rows onClick? item? itemSlot?`   | `onClick` and `item` are shaped `[cells]`; `item` fills the cell's `itemSlot` (1-based)  |
| `Collection bind`, `Slots span claim?`, `Hotspot`       | industrial slot frames; `Slots claim="all"` blocks clicks on its slots                   |
| `Window name container title? inventory? frame?`        | the window in industrial's shell; see below                                              |
| `Prompt name bind onConfirm onBack? label? title?`      | an anvil text prompt in the window; see [Native anvil search](#native-anvil-search)      |
| `Container`, `Player`, `Hotbar`                         | the slot sections                                                                        |
| `Header`, `Row`, `Column`, `Grid`, `Center`, `Spacer`   | layout boxes                                                                             |
| `Show when`                                             | draws its children while a condition holds                                               |

- `Window` takes the primitive's props except `bleed` and `style`, and places its shell from
  `containerLayout(container)`: a raised `frame` (default `art.shell`) with corner rivets and a hazard bar along its
  bottom, `title` in a recess along the top edge, a panel under an anvil's input and slots, and a panel under the
  player's inventory. `inventory={false}` claims the player and hotbar slots instead (so it rejects its own `<Player>`
  and `<Hotbar>`); an anvil then ends its shell below the slots. That relies on the pack hiding vanilla's anvil art,
  which any pack with an `<Input>` does. Labels default to white small caps with a shadow.
- Controls (`Button`, `Toggle`, `Choice`, `Tabs`, `Repeater` cells) inset their slot cells by 1px, so their face covers
  the 16x16 slot interiors, and center their content in a row (a column in a repeater cell) with centered labels.
  `frame`, `padding`, `gap`, `text`, `tooltip`, and `itemModel` style the face; a state's `frame` or `tooltip` replaces
  them in that state. State frames are drawn at the control's size.
- A face centers its content as CSS does, rounding odd leftover pixels to the nearest pixel. To place content one pixel
  further left, as the runtime places text in a fixed width, give the content a fixed width: a label as wide as the
  face, or an icon in a box one pixel wider than it.
- `art` holds the frames `shell`, `panel`, `recess`, `slot`, `button`, `buttonSelected`, `buttonDisabled`,
  `buttonAccent`, `buttonDanger`, `buttonConfirm`, `hud`, and `hazardBar`, and the images `rivet` (5x5), `lampOn` and
  `lampOff` (4x4), `slotSelected` (18x18), and `inputField` (110x16, for the `vanilla.anvil.field` plugin option).
- `raised(fill, options?)` and `sunken(fill, options?)` are the bevel recipes behind them, and `tones` their light and
  dark tones.

### Variant contracts

Each control's `style` takes the [variants](#styles) it names, each a box style; a group with another variant is a type
error. Industrial's own styles, its `styles` export, come first, and `style` adds to them.

| component        | variants                         |
| ---------------- | -------------------------------- |
| `Button`         | `base`, `disabled`               |
| `Toggle`         | `base`, `on`, `off`              |
| `Choice`, `Tabs` | `base`, `selected`, `unselected` |
| `Repeater`       | `cell`                           |

```tsx
const ghost = variants({
  base: { frame: art.recess, padding: 2 },
  disabled: { frame: art.slot },
});

<Button onClick={buy} enabled={canBuy} style={ghost}>
  Buy
</Button>;
```

### Theming industrial

Industrial's `colors` are [vars](#vars-and-themes), and every industrial art value derives from them, so a theme
recolors the art under it:

```tsx
const ember = createTheme(colors, { panel: "#8c3a1c", button: "#c0503a" });

<Box theme={ember}>…</Box>;
```

The vars are `border`, `highlight`, `shell`, `panel`, `recess`, `slot`, `button`, `selected`, `disabled`, `accent`,
`danger`, `confirm`, `hud`, `lamp`, `hazard`, `hazardStripe`, `rivet`, `rivetHighlight`, and `rivetShadow`.

Art Kotlin selects at runtime, such as lamp images for a `sprite` handle, goes in the [sprite catalog](#sprite-catalog).

## Handles

A handle declares one binding and the Kotlin member it generates. Declare handles in an ordinary module and pass them to
JSX props; the id is explicit because a handle cannot see the variable it is assigned to. Every bound prop takes a
handle: a binding name is a type error.

```tsx
import { action, flag, selection, text } from "plugin:window/bind";

export const category = selection("category", ["all", "gear", "magic"], { initial: "gear" });
export const canBuy = flag("can_buy");
export const buy = action("buy");
export const title = text("title");
```

```tsx
<Text bind={title} />
<Tabs bind={category} span={3}>{(value) => <Text>{labels[value]}</Text>}</Tabs>
<Switch on={category}>{{ all: <A />, gear: <B />, magic: <C /> }}</Switch>
<Switch on={canBuy}>{{ true: <Image art={lampOn} />, false: <Image art={lampOff} /> }}</Switch>
<Show when={category.is("gear")}><Image art={gearBadge} /></Show>
<Button onClick={buy} enabled={canBuy} disabled={{ tooltip: "Not enough coins" }}>Buy</Button>
<Region onClick={category.set("magic")} tooltip="Magic" />
<Button close>Exit</Button>
```

| handle                                | used by                                                  | Kotlin member                                                           |
| ------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------- |
| `flag(id)`                            | `<Switch on>`, `Show when`, `Button enabled`             | `protected abstract fun canBuy(): Boolean`                              |
| `toggle(id, { initial? })`            | `onClick`, `Toggle bind`, `<Switch on>`, `Show when`     | `protected var favorites: Boolean by state(…)` and `onFavoritesChanged` |
| `value(id, values)`                   | `<Switch on>`, `.is(v)`                                  | `enum class Mode` and `protected abstract fun mode(): Mode`             |
| `selection(id, values, { initial? })` | `<Switch on>`, `Tabs bind`, `Choice bind`, `.is`, `.set` | `enum class Category`, `protected var category` and `onCategoryChanged` |
| `text(id)`                            | `<Text bind>`                                            | `protected abstract fun title(): Component`                             |
| `sprite(id, { only? })`               | `<Image bind>`                                           | `protected abstract fun iconSprite(): WindowSprite?`                    |
| `tint(id, palette)`                   | `tint` of a box, case, image, or bar; text `color`       | `enum class Tone` and `protected abstract fun tone(): Tone`             |
| `fraction(id)`                        | `<Bar bind>`                                             | `protected abstract fun health(): Float`                                |
| `items(id)`                           | `<Items bind>`                                           | `protected abstract fun stack(): ItemStack?`                            |
| `collection(id, { selectable? })`     | `<Collection bind>`                                      | `protected abstract val products: WindowCollection<ItemStack>`          |
| `action(id)`                          | `onClick` of a region or control                         | `protected abstract fun onBuy(click: Click)`                            |
| `input(id)`                           | `<Input bind>`                                           | `protected abstract fun onQueryChanged(value: String)`                  |
| `builtin("window:close")`             | `onClick`; `Button close` is shorthand                   | none; the runtime closes the window                                     |

- A view declares one member per handle its window or HUD uses and binds every use to it, so one handle may drive many
  elements and windows. Handles sharing an id must agree on kind, values, initial value, and shape; anything else is a
  build error.
- Each use of a handle is one entry of the compiled definition, named after the handle: `title`, then `title~2`,
  `title~3` for later uses in the same window. A condition's entry is named `id?value` (`category?gear`), and a click
  setting a selection `id=value`. Generated views bind every entry; hand-written views bind them by these names.
- `toggle` and `selection` are runtime state the UI owns. `initial` defaults to `false` or the first value. A click that
  changes the state calls `on…Changed(value)` afterwards; assigning the property from Kotlin does not. HUDs cannot use
  them.
- `.is(value)` is a condition for `<Switch bind>`, `Show when`, and `Button enabled`; `.set(value)` is a click. Values
  outside the handle's list are type errors, and `<Switch on>` needs a case for every value, or `true` and `false` for a
  flag or toggle.
- `collection` handles do not take a shape, and a `<Collection selected>` sprite requires `selectable: true`. The view
  exposes the cell count as `ShopView.PRODUCTS_SIZE` when every collection the handle binds has the same count.
- `text`, `sprite`, `toggle`, `items`, `collection`, and `input` only declare handles; the `raw` elements are
  `raw.text`, `raw.image`, `raw.items`, `raw.collection`, and `raw.input`, and the small-caps helpers are
  `raw.text.smallCaps`.

### Indexed handles and repeaters

`flag`, `value`, `text`, `sprite`, `fraction`, `items`, and `action` take `shape: [n]` or `shape: [rows, columns]`. Read
an entry with `.at(i)` or `.at(row, column)`; the Kotlin member takes `index: Int` or `row: Int, column: Int`, and an
indexed action receives an `IndexedClick` whose `index` is the entry, row-major. The view exposes each shape as
constants: `ShopView.ENTRY_STACK_SIZE`, or `_ROWS` and `_COLUMNS`. Entries are named `entry_stack[3]` or
`strokes[1][4]`.

```tsx
export const pickEntry = action("pick_entry", { shape: [6] });
export const entryStack = items("entry_stack", { shape: [6] });
export const entryName = text("entry_name", { shape: [6] });

<Repeater cell={[3, 2]} columns={3} rows={2} onClick={pickEntry} item={entryStack} itemSlot={2}>
  {(i) => <Text bind={entryName.at(i)} width={50} />}
</Repeater>;
```

A repeater whose children are a function renders each cell, row-major, with its index. Its cells click into `onClick`,
an action shaped `[cells]`, everywhere but the `itemSlot`, which shows the cell's `item` stack. Every indexed handle
read inside its cells must have as many entries as the repeater has cells.

### Tints

`tint(id, palette)` names a fixed set of colors, and Kotlin picks which one is drawn. A `tint` prop colors art with it,
and a text `color` takes it.

```tsx
import { text, tint } from "plugin:window/bind";

export const tone = tint("tone", { ok: "#3ddc84", warn: "#ffb020", danger: "#ff4d4d" });

<Box frame={art.pill} tint={tone} padding={3}>
  <Text bind={text("time")} width={60} color={tone} />
</Box>
<Image art={art.icon} tint={tone} />
```

```kotlin
override fun tone(): Tone = if (remaining > 3) Tone.OK else Tone.DANGER
```

- A tint multiplies: each pixel's red, green, and blue are scaled by the tint's, and alpha is kept. White art takes the
  color exactly, grey art a darker shade of it, and black stays black, so author tinted art in white and greys. Art that
  already has a hue is filtered by the tint rather than recolored.
- The palette is fixed at build time: one to 64 entries, each a `#rrggbb` color named like a `value` handle's values.
  Kotlin returns an entry of the generated enum, not a color, and the color changes on the next render.
- `tint` goes on a `<Box>` or `<Case>` with a `frame`, on `<Image art>`, and on `<Image bind>`, which takes only a
  handle. A hex `tint` on art is baked into its texture and costs nothing at runtime. A window, HUD, section, or
  collection frame cannot be tinted; wrap or cover it with a tinted box instead.
- Text takes a tint as its `color`, on bound and static text and in `text={{ color }}` defaults. It replaces the colors
  inside a runtime text value in a shader-placed HUD, like any other color there.
- Art tinted by a handle leaves the static art and becomes a layer of its own, drawn at its place in the
  [draw order](#draw-order). Adjacent art of one tint shares a layer, and each layer is one more texture of its pane or
  switch case.
- In a shader-placed HUD each tinted art layer and each tinted text adds one entry per palette entry to the generated
  shader's table, so a three-color tint on a frame and its text costs six. Menus and HUDs without a shader send the
  palette color itself and cost nothing more.

### Bars

`<Bar>` draws a progress bar: its `fill` art, revealed from the left up to the fraction a `fraction` handle returns.

```tsx
import { fraction, tint } from "plugin:window/bind";

const health = fraction("health");
const tone = tint("tone", { ok: "#3ddc84", low: "#ff4d4d" });

<Bar bind={health} width={80} height={5} fill={art.barFill} track={art.barTrack} tint={tone} />;
```

```kotlin
override fun health(): Float = player.health / player.maxHealth

override fun tone(): Tone = if (health() > 0.25f) Tone.OK else Tone.LOW
```

- `width` and `height` are pixels, each from 1 to 256. `fill` and the optional `track` are [inline art](#inline-art),
  stretched over the bar like a box's `frame`; the track is drawn whole, under the fill.
- The fraction is clamped to 0 through 1 and rounded to the nearest whole column of `width`, so an 80 pixel bar has 81
  states. The view redraws only when the column count changes.
- The fill is revealed, not rescaled: a fraction draws the leftmost columns of the full-width art exactly as they look
  in the full bar. Rounded ends, borders, gradients, and textures all work; the right end of the art shows only when the
  bar is full, so give the fill square ends unless that is the look you want.
- `tint` multiplies the fill like any other [tint](#tints): a hex color is baked in, and a `tint` handle picks the color
  at runtime. Color thresholds are a tint handle whose entry Kotlin picks from the same value, as above; there is no
  separate thresholds option.
- A bar works in windows and HUDs, including shader-placed HUDs and switch cases. Its fill is an art layer, drawn at its
  place in the [draw order](#draw-order). In an `anvil` window with an `<Input>`, a bar needs
  `experimental.anvilUpdates`, like any other title change.
- Cost: the fill is cut into clips of 1, 2, 4, … columns, and each column count is drawn from at most one clip per size.
  Clips that look the same share a texture, so a fill that is uniform along its width costs one small texture per size,
  7 for a 100 pixel bar. Art that differs from column to column costs up to one texture per column, so keep gradients
  and textured fills narrow, or uniform in the middle.

## Raw API

`raw` builds the same primitives as JSX with plain function calls, positioned by hand or laid out by `box` and
`section`. It builds the same documents as JSX, so both styles can be mixed in one pack, and industrial components are
called as functions.

The primitives `ui`, `hud`, `box`, `text`, `image`, `region`, `items`, `collection`, `switchOn`, `case`, and `section`
take a `style` field with the same [styles](#styles) as their JSX primitive; explicit fields win, and an explicit
`layout` merges over the style's item properties per field. `ui`, `hud`, `box`, and `case` take a `theme`, and vars
resolve when `ui` or `hud` builds its document.

### Windows

```ts
import { action, builtin, text } from "plugin:window/bind";
import * as raw from "plugin:window/raw";
import { Button, art } from "plugin:window/theme/industrial";

export default raw.ui({
  name: "shop",
  container: "generic_9x6",
  bleed: { top: 12, right: 8, bottom: 16, left: 8 },
  children: [
    raw.box({ frame: art.hazardBar, x: -8, y: 216, style: { width: 192, height: 18 } }),
    raw.box({ frame: art.panel, x: 0, y: 0, style: { width: 176, height: 222 } }),
    raw.text(text("title"), { x: 8, y: 6, width: 160, align: "center", color: "#ffd700" }),
    raw.section("hotbar", {
      children: [
        Button({ onClick: action("buy"), span: 6, children: raw.text(text("buy_label")) }),
        Button({
          onClick: builtin("window:close"),
          span: 3,
          tooltip: "Close",
          children: raw.text("Close", { width: 52 }),
        }),
      ],
    }),
  ],
});
```

### HUDs

HUDs use the same visual primitives as windows: boxes, text, images, and switches. They have no inventory, so slot
primitives belong in windows. They render to a fixed-width line and are sent through a vanilla fallback channel
(`"actionbar"`, `"bossbar"`, or `"sidebar"`). Dynamic text values are Adventure components on the server side, just like
window text.

```ts
import { text } from "plugin:window/bind";
import * as raw from "plugin:window/raw";
import { art } from "plugin:window/theme/industrial";

export default raw.hud({
  name: "status",
  channel: "actionbar",
  width: 160,
  height: 34,
  children: [
    raw.box({ frame: art.hud, x: 0, y: 0, style: { width: 160, height: 16 } }),
    raw.text("Coins", { x: 8, y: 4, width: 44, color: "#ffd700" }),
    raw.text(text("coins"), { x: 54, y: 4, width: 98, align: "right", color: "#ffffff" }),
    raw.box({ frame: art.recess, x: 0, y: 18, style: { width: 92, height: 16 } }),
    raw.image(art.lampOn, { x: 6, y: 24 }),
    raw.text("Power", { x: 16, y: 22, color: "#ffd700" }),
    raw.text(text("power"), { x: 52, y: 22, width: 34, align: "right", color: "#ffffff" }),
  ],
});
```

If the plugin option `coreShaders: { hud: true }` is set, a HUD may also include
`shader: { source_bottom: 59, origin: { x: 0.5, y: 0.08 }, anchor: { x: 0.5, y: 0.0 } }`. `origin` is a normalized GUI
point (`0.0` is left/top, `1.0` is right/bottom); `anchor` is the normalized point inside the HUD surface placed on that
origin. Optional `x`/`y` values add a GUI-pixel nudge from the normalized origin. `source_bottom` is the GUI-pixel
distance from the bottom of the GUI to the nominal bottom of the vanilla text source. Window applies Minecraft's fixed
actionbar source inset when deriving its top edge; the source position does not change with the authored HUD height. See
[Roots](#roots) for how shader-placed HUDs share text rows and how large a pane's art may be. Window then emits
generated text core shaders for the pack's `pack.format` (the `max` of a range), including the matching text-background
pass so vanilla actionbar backdrops do not sit behind relocated HUD glyphs. Shader profiles cover pack formats 9 through
88 (Minecraft 26.2); compilation fails when a shader-placed HUD targets an unsupported pack format or `coreShaders.hud`
is not enabled. Core shaders are intentionally opt-in; the fallback channel remains the runtime contract.

Every constructor except `ui`, `hud`, `case`, `input`, and `section` also takes `layout`, its item layout inside a box,
section, or switch case. Every element takes `debug_name`. `tooltip` is a string or `{ title: "...", lines: [...] }`.

### Box layout

`box()` is the CSS box behind JSX `<Box>`, and `section()` behind `<Section>`. `style` takes the same properties as
`<Box>` (`direction`, `justify`, `align`, `gap`, `padding`, `width`, `minWidth`, `columns`, `flow`, …), and each child
sets its own `layout` in snake case (`grow`, `align_self`, `margin`, `position`, `column`, `row`, `translate`, …). JSX
`span={n}` is `layout: { column: { span: n } }`, `at={[x, y]}` is the one-based lines `column: x + 1, row: y + 1`,
`absolute` is `position: "absolute"`, and `grow` must be a number. Unlike `<Collection>`, `raw.collection()` covers one
slot unless its `layout` spans more, e.g. `column: { start: 1, end: -1 }`.

```ts
raw.section("container", {
  frame: art.panel,
  children: [
    raw.collection(collection("products"), {
      frame: art.slot,
      layout: { column: { start: 1, end: -1 }, row: { span: 3 } },
    }),
    raw.box({
      frame: art.recess,
      style: { direction: "row", align: "center", padding: { left: 4, right: 4 } },
      layout: { column: { span: 9 } },
      children: [raw.text(text("selection")), raw.text(text("price"), { width: 40, align: "right" })],
    }),
  ],
});
```

### Draw order

Window draws the static chrome first, then every runtime layer in authored tree order: text, runtime sprite slots,
switch case art, art layers, and collection selections. Later elements draw above earlier ones, so anything authored
after a switch draws above its case art. Elements in a box draw in authored order whether they flow or set `x`/`y`.

Art with a [`tint` handle](#tints) and the fill of a [bar](#bars) are art layers, so they draw above the static chrome
and above the text and switches authored before them. Untinted art authored after one that overlaps it becomes an art
layer too and draws above it; all other untinted art stays in the static chrome underneath. Inside a switch case the
same holds within the case's art.

`WindowView.list(...)` creates a `WindowList` that pages or scrolls a reactive list through a fixed number of cells and
keeps its selection by key; its `items(...)` adapts it to a `collection` handle, and `canPrevious()`/`canNext()` back
the `flag` handles of `Button enabled` previous/next buttons.

## Text overflow

Bound text can fit itself to its slot at runtime, measured with the slot's own font and style:

```tsx
<Text bind={name} overflow="ellipsis" width={46} />
<Text bind={name} lines={2} lineHeight={7} width={46} smallCaps />
```

```ts
raw.text(name, { width: 46, overflow: "ellipsis" });
raw.text(name, { width: 46, lines: 2, line_height: 7, small_caps: true });
```

- `overflow: "ellipsis"` truncates content wider than the slot and appends "…" (or "..." when the slot's font has no
  "…"). The kept text keeps its colors, decorations, and fonts. Content that fits is drawn unchanged.
- `lines` wraps content at spaces onto at most that many lines. The last line, and any single word wider than the slot,
  ends in an ellipsis, so `lines` above 1 implies `overflow: "ellipsis"`. `lineHeight` (`line_height`) is the distance
  between line tops and defaults to 9, the vanilla line spacing.
- A slot with `lines: n` is `(n - 1) * lineHeight + 8` pixels tall in layout. The lines a value uses are vertically
  centered in that box, so a short value sits in its middle and a long one fills it.
- `lines` must be at least 1, and like any dynamic text the slot needs a `width` unless its parent sizes it. Fitting
  only applies to bound text: setting these options on static text is a build error.
- Fitting works in windows and HUDs, including shader HUDs, switch cases, and indexed handles.

When a slot must keep a suffix while shortening the text before it, such as `"<holder> - 42"`, fit the value in Kotlin
instead: `WindowView` and `HudView` provide `fit(slot, value, suffix)`, which shortens `value` with an ellipsis so that
it and `suffix` fit the slot, then appends `suffix`. `slot` is the entry name, such as `name` or `name[2]`.

## Conditionals

A switch draws one of its cases, chosen at runtime by a handle: `<Switch bind><Case value>` or
`raw.switchOn(on, cases)`, and `<Switch on>` with its cases keyed by value. Industrial's `Show when` is a switch with a
`true` case holding its children and an empty `false` case.

```tsx
<Switch bind={mode}>
  <Case value="buy">
    <Box direction="row" frame={art.recess}>
      <Text>Buy</Text>
      <Text bind={price} />
    </Box>
  </Case>
  <Case value="sell">
    <Box direction="row" frame={art.buttonAccent}>
      <Text>Sell</Text>
      <Text bind={payout} />
    </Box>
  </Case>
</Switch>
```

```ts
raw.switchOn(mode, {
  buy: { frame: art.recess, children: [raw.text("Buy"), raw.text(price)] },
  sell: { frame: art.buttonAccent, children: [raw.text("Sell"), raw.text(payout)] },
});
```

- Every case is laid out in the same box. On its own the box takes the largest case's size; an unpositioned switch
  directly inside a box fills that box's content instead. Auto-sized cases stretch to fill the box, while cases with an
  explicit `width`/`height` keep it. The space is always reserved, like CSS `visibility: hidden`, so siblings never move
  at runtime.
- A case is a column box. `<Case>` takes box props such as `frame`, `justify`, and `align`. `switchOn` cases take
  `frame`, `style` (`direction` defaults to `"column"`), and `children`; `switchOn` takes `x`/`y` (set both).
- Cases hold any visual primitive, other switches, and the slot primitives `<Region>`, `<Items>`, and `<Collection>`,
  which claim their slots only while their case is drawn (see [Primitives](#primitives)). A switch inside a case is
  shown only while that case is. Anvil inputs inside cases are build errors.
- A handle may appear in several cases, such as a label repeated in each state of a control: each use is its own entry
  (`label`, `label~2`) with its own position and style, which lets a shader HUD give one value a different color per
  case, and a generated view fills both from one member.
- Each case's art becomes its own layer, drawn at the switch's place in the [draw order](#draw-order). Windows redraw
  the title when the case changes, and a HUD draws the new case on its next `render()`.
- Generated Kotlin returns the active case: an enum of the case values (`protected abstract fun mode(): Mode` with
  `enum class Mode { BUY, SELL }`), or `Boolean` for a flag or toggle (`protected abstract fun onSale(): Boolean`).
  Views without generated bindings use `WindowScope.switch(entry) { value }` or `HudScope.switch`.

## Native anvil search

Use the `anvil` surface when a UI needs real keyboard input. Window seeds the first anvil slot, keeps it owned by the
input, receives the text box contents from the host, and calls the `input` handle's member.

A pack with an `<Input>` hands every anvil screen to Window: it replaces vanilla's anvil background and missing-result
icon with transparent textures, so only Window art shows, and vanilla anvils no longer draw their own GUI.

Anvil input windows are static: their title never changes after open. Vanilla can only change a container title by
reopening the screen, and each anvil reopen resets the player's edit box mid-typing. The compiler rejects bound text,
sprite slots, switches, and collection selected sprites in a window with an input. Static art, labels, regions, and
inventory items are all allowed, since none of them change the title.

A typical search screen is a title, the input, and buttons on the anvil's three slots. Anvil slots sit at fixed, uneven
positions, so each button covers one slot and only that slot's 16x16 box takes clicks. A region over the input's slot
routes its clicks while the input keeps the slot's item, which shows no tooltip. Claiming the player's slots hides their
items, so the screen ends where the art does. Industrial's `<Window inventory={false}>` claims the player and hotbar
slots this way, and its `Window` draws the anvil's panel under the input and slots.

Industrial's `Prompt` is that screen ready-made: an `inventory={false}` anvil `Window` with `<Input bind initial?>`, a
static `label` left of the field, a back button on the first anvil slot when `onBack` is set, and an `art.buttonAccent`
confirm button on the third. `back` and `confirm` replace the buttons' content (`"<"` and `"OK"`), `confirmTooltip` sets
the confirm tooltip, and `children` are drawn after the prompt's own content.

```tsx
import { Prompt } from "plugin:window/theme/industrial";

<Prompt name="catalog_search" title="Catalog Search" label="Name" bind={query} onConfirm={confirm} onBack={back} />;
```

A callback-style view hands the result back to its opener:

```kotlin
class CatalogSearch(player: Player, private val initial: String, private val done: (String?) -> Unit) :
    CatalogSearchView(player) {
    private var query = initial

    override fun onOpen() {
        if (initial.isNotEmpty()) input("query", initial)
    }

    override fun onQueryChanged(value: String) {
        query = value.trim()
    }

    override fun onConfirm(click: Click) = done(query)

    override fun onBack(click: Click) = done(null)
}
```

The raw form:

```ts
export default raw.ui({
  name: "map_search",
  container: "anvil",
  children: [
    raw.box({ frame: art.shell, x: 0, y: 0, style: { width: 176, height: 70 } }),
    raw.text("Search maps", { x: 0, y: 6, width: 176, align: "center" }),
    raw.input(input("query"), { initial: "" }),
    raw.section("container", {
      claim: "none",
      children: [
        Button({
          onClick: action("back"),
          at: [0, 0],
          style: { base: { frame: art.buttonDanger } },
        }),
        Button({
          onClick: action("confirm"),
          at: [2, 0],
          style: { base: { frame: art.buttonConfirm } },
        }),
      ],
    }),
    raw.section("player", { claim: "all" }),
    raw.section("hotbar", { claim: "all" }),
  ],
});
```

Generated views expose `onQueryChanged(value: String)`. Hand-written views bind the same input with
`anvilInput("query") { value -> ... }`. Every edit reaches the binding as the player types. Views set the text with
`input("query", value)`, for example to restore a previous query in `onOpen` or to clear it; the player's edit box
updates in place and the binding receives the value.

Window keeps the client's own rename box visible, with its cursor, selection, and font: in every window with an input,
the field's rect (59, 20, 110x16) stays transparent in Window's art. Text drawn over that rect produces a warning. The
plugin option `vanilla.anvil.field: "<sprite>"` names a 110x16 [catalog sprite](#sprite-catalog) that replaces vanilla's
anvil text-field sprites for the whole pack; industrial's `art.inputField` is one, registered in `sprites`. See
[Plugin options](#plugin-options) for `vanilla.anvil.background` and the rest of the `vanilla` rule.

The plugin option `experimental: { anvilUpdates: true }` lifts the static-title rule. Title changes then reopen the
anvil: Window holds them until the player pauses typing and rebases edits typed during a reopen, but the screen can
still flicker, keystrokes can still be lost, and each reopen moves the cursor to the end. `input` also reopens the
anvil.

## Slot Patterns

Sections place most slot primitives. Items and collections may instead take slot-space patterns, which are zero-based
grid coordinates in a visible section:

- `container`: the opened container grid, backed by container slots `0..`.
- `player`: the visible 3x9 player inventory, backed by player slots `9..35`.
- `hotbar`: the visible 1x9 hotbar, backed by player slots `0..8`.

```ts
raw.collection(collection("pets"), {
  frame: art.slot,
  selected_sprite: art.slotSelected,
  pattern: pattern.rect({ section: "container", x: 1, y: 1, width: 7, height: 2 }),
});
```

`selected_sprite` is art that marks one cell at runtime, drawn over the cell's 18x18 slot box above the static frame and
below the item. The generated view gains `protected open fun petsSelected(): Int?`, returning the cell index to mark or
`null` for none.

Available constructors:

```ts
pattern.rect({ section: "container", x: 2, y: 2, width: 5, height: 4 });
pattern.slots([10, 11, 12, 19, 20, 21], { section: "container" });
pattern.grid({ section: "container", x: 0, y: 2, columns: 3, rows: 2, cell_width: 3, cell_height: 2 });
```

`transform: { ... }` is inline shorthand for a rectangular pattern. Raw slot refs remain available as an escape hatch:

```ts
raw.collection(collection("pets"), {
  slots: [containerSlot(10), containerSlot(11), containerSlot(12), playerSlot(9), playerSlot(10), playerSlot(11)],
});

raw.items(items("egg_info"), { slots: [containerSlot(4)] });
```

`containerSlot(index)`, `playerSlot(index)`, and `hotbarSlot(index)` return typed slot references. The plural helpers
(`containerSlots`, `playerSlots`, and `hotbarSlots`) build inclusive ranges that the compiler expands after validating
both endpoints. For convenience, raw integers inside `slots` are accepted as container slots.

An `<Items>` stack draws a real `ItemStack`, with its true 3D model, above Window's title-composed art. Its own name and
lore become that slot's tooltip, which is vanilla behaviour; suppress it with the item's own `minecraft:tooltip_display`
component. Clicks on an items slot reach no handler; a card that should take clicks on its stack uses a `<Collection>`,
whose clicks carry the cell index.

## Text helpers and glyphs

Text conversion helpers are plain string functions:

```ts
raw.text.smallCaps("Shop");
raw.text.smallCapsMinimessage("<gold>Shop</gold>");
```

Window's shifted label fonts cover printable ASCII, the remaining glyphs on Minecraft's `ascii.png` sheet (Latin-1
symbols, box drawing, and math symbols such as `±`, `°`, and `≤`), the glyphs emitted by the small-caps helpers, and the
standard UI markers/separator `×`, `▲`, `▼`, `◆`, `●`, and `·`. Their advances are measured from the rightmost opaque
cell pixels in the built-in bitmap sheets shipped by Minecraft 26.1.2 and 26.2 so every label segment returns the title
cursor to the same origin. Runtime text outside that set logs an unsupported-glyph warning; use a Window image for
additional iconography instead of relying on Minecraft's missing-glyph fallback.

## Semantics

- Text is 8px tall. Static text defaults to its measured width; dynamic text requires `width` unless its parent box
  sizes it.
- Images use their bitmap texture's intrinsic size, or the shape's authored `width` and `height`.
- `x` and `y` position an element relative to its parent box's content origin and remove it from flow.
- Handle ids must match `^[a-z][a-z0-9_]*$`.
- Unknown fields, and fields that belong to a different element or pattern kind, are rejected by the compiler. This
  applies even when plain objects are passed directly through `raw.ui` or `raw.hud`. Frame and image fields take only
  art values; a string is rejected.
- `color` is `#rrggbb` or a [`tint` handle](#tints); default text color is `#404040`; `shadow` defaults to `false`.
- Text `bold`, `italic`, `underlined`, `strikethrough`, and `obfuscated` default to `false`. Bold changes measured
  width; the other decorations are visual style only.
- `font` draws text with a [text font](#text-fonts), and `small_caps: true` with the bundled small-caps font; setting
  both is an error. Text is measured with the font's glyphs, and runtime values use the same font. Author and send plain
  text (`"Buy 20"`).
- Runtime text values are Adventure components. Child colors, decorations, and fonts are preserved for window titles,
  and measured from the generated pack definition's per-font metrics. Shader HUDs force generated marker colors so the
  shader can relocate text; decorations and font keys are still measured.
- Runtime text values must contain only text components. Translatable, keybind, score, selector, NBT, and object
  components fail with `IllegalArgumentException` because only the client knows their text; render them first, for
  example with `GlobalTranslator.render(component, locale)`. Legacy `§` codes in text are measured like the client: they
  draw nothing, `§l` adds bold width, color codes clear bold, and `§r` restores the component's own style.
- `container` is one of `generic_9x1` through `generic_9x6`, or `anvil` for one native rename input.
- `bleed` on a window/HUD allows static drawings to extend outside the normal surface without warnings. Text and
  interactive regions must still stay inside the real surface.
- HUD `channel` is one of `actionbar`, `bossbar`, or `sidebar`; default is `actionbar`.
- Pattern section coordinates are zero-based. `player` addresses the visible main inventory only; use `hotbar` for
  player slots `0..8`.
- Sections preserve Minecraft's native vertical gutters. For a generic 9xN screen, the container/player gutter is 16px
  and the player/hotbar gutter is 6px. Anvil screens reserve 21px and 6px respectively.
- A region routes clicks on every slot it covers and fills its hitbox item into those whose stacks no items, collection,
  or anvil input owns; those keep their own stacks, and the input its seed item.
- Player inventory slots are temporarily taken over by the runtime while the menu is open and restored when it closes.
  Use these for menu controls in the visible player inventory area, not for permanent inventory mutation.
- Window emits an invisible `{namespace}:gui/hitbox` item model for region hitboxes. Hover tooltips are native Minecraft
  inventory tooltips, so they appear wherever the region's slots are hovered.

## Migration

The theme table, presets, string bindings, and the compiler's widgets are gone. Every window is primitives, handles,
inline art, and `industrial` components:

| before                                                                                    | now                                                                                               |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `theme({ frames, sprites })`, `frame="panel"`, `<Sprite name>`                            | [inline art](#inline-art) values: `frame={art.panel}`, `<Image art={coin} />`                     |
| `presets.industrial(options)`                                                             | industrial `art`, recolored with `createTheme(colors, …)`                                         |
| theme sprites Kotlin selects                                                              | `defineWindows({ sprites })`, the [sprite catalog](#sprite-catalog)                               |
| theme `fonts`                                                                             | `defineWindows({ fonts })`; `<Text font="runes">` is unchanged                                    |
| theme `colors` and `WindowColors`                                                         | removed; keep palettes in Kotlin                                                                  |
| `defineWindows({ themes })`                                                               | removed; a `themes` field is a build error                                                        |
| `bind="title"`, `name="buy"`, `when="on_sale"`, `index`                                   | [handles](#handles): `bind={text("title")}`, `onClick={action("buy")}`, `.at(i)`                  |
| `<Button>`, `<Toggle>`, `<Choice>`, `<Tabs>`/`<Tab>`, `<Hotspot>`, `<Repeater>`, `<Show>` | the `industrial` components of the same names                                                     |
| `<Container>`, `<Player>`, `<Hotbar>`, `<Header>`, `<Slots>`                              | `<Section of>` or the `industrial` components                                                     |
| `<Row>`, `<Column>`, `<Grid>`, `<Center>`, `<Spacer>`                                     | `<Box>` props, or the `industrial` layout boxes                                                   |
| `<Sprite>`, `<Icon>`, `<Item>`, `<AnvilInput>`                                            | `<Image art>`, `<Image bind size>`, `<Items bind>`, `<Input bind>`                                |
| `raw.panel`, `row`, `column`, `flex`, `grid`                                              | `raw.box`                                                                                         |
| `raw.label`, `raw.slot`, `raw.sprite`, `raw.spriteSlot`                                   | `raw.text`, `raw.image`                                                                           |
| `raw.button`, `toggle`, `choice`, `hotspot`, `repeater`, `slotRects`, `show`              | industrial `Button(…)` and the other components called as functions, or `raw.region` in a section |
| `raw.item`, `raw.anvilInput`                                                              | `raw.items`, `raw.input`                                                                          |
| a button's `pattern`/`transform` or `x`/`y`/`width`/`height`                              | its place in a `section` (`at`, `span`), or a region in a positioned box                          |
| a fixed sprite slot                                                                       | `<Image art>`, or a `<Box frame>` of the sprite's declared size when its texture is another size  |

Authoring imports moved from `#plugins/window` to its modules: `plugin:window/ui`, `plugin:window/bind`,
`plugin:window/raw`, and `plugin:window/theme/industrial`, whose components are imported by name (`industrial.Button` is
`Button`). `rpp.config.ts` imports `plugin:window` and `rpp:config`.

Centering changed for content that does not fill its box: legacy buttons centered children by floor division, while a
box centers with CSS rounding, so content with an odd leftover width sits one pixel further right. Give such content a
fixed width, as the [industrial](#industrial) notes describe, to keep its pixels.

Generated Kotlin is built from handles only. The abstract members of handles are unchanged, including `canBuy()`,
`var favorites`, `var category`, and `on…Changed`. What changes:

- Button bindings are `switch(…)` and `button(…)` entries in place of `enabledButton`, `toggle`, and `choice`. Content
  repeated in each state of a control binds once per state: a bound `<Text>` in a toggle generates text entries `label`
  and `label~2`, both filled from the same member.
- A disabled button's slots take no clicks rather than calling a disabled handler.
- `WindowSprite` lists only [sprite catalog](#sprite-catalog) entries.
- Section claims are named after their section (`player_section`) rather than a `<Slots name>`.
- `WindowColors` is no longer generated.

The JVM runtime drops the helpers that served named controls: `WindowScope.buttonItem`, `buttonState`, `tooltip`,
`toggle`, `choice`, and `enabledButton`, and `WindowView.buttonItem`, `buttonState`, and `tooltip`. Hand-written views
bind entries with `switch`, `button`, `slot`, `sprite`, `item`, `collection`, and `anvilInput`, and set a region's
tooltip in its source. The compiled definition is schema version 9; regenerate packs and Kotlin together.
